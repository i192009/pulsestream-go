# Kubernetes, Helm and Kind

The chart deploys all six backend roles, dashboard, configuration, Secret references, Services, startup/liveness/readiness probes, resources, init Job, optional Ingress, replica-dependent PodDisruptionBudgets, NetworkPolicy and optional KEDA scaling. It expects Redpanda, PostgreSQL, ClickHouse and Redis endpoints; the development dependency manifests are supplied separately. Those dependencies are single replicas with PVCs, not a high-availability topology.

```bash
python scripts/tasks.py helm-lint
helm template pulse deployments/helm/pulsestream > rendered.yaml
kubectl create namespace pulsestream
kubectl -n pulsestream apply -f deployments/kubernetes/dependencies.yaml
kubectl -n pulsestream create secret generic pulsestream-secrets \
  --from-literal=PULSE_KEYS=replace-me:tenant-demo:admin \
  --from-literal=PULSE_DATABASE_URL='postgres://pulse:pulse-dev@postgres:5432/pulse?sslmode=disable' \
  --from-literal=PULSE_CLICKHOUSE_PASSWORD=pulse-dev
helm upgrade --install pulse deployments/helm/pulsestream -n pulsestream --wait --timeout 5m
kubectl -n pulsestream get pods,svc,jobs
kubectl -n pulsestream port-forward svc/pulse-dashboard 13000:8080
```

For local image use, load `pulsestream-go:dev` and `pulsestream-dashboard:latest` into the cluster. `python scripts/tasks.py kind-deploy` creates a dedicated Kind cluster, builds and loads both images, deploys local dependencies, provisions the development Secret and installs the chart. It requires `kind`, `kubectl`, `helm` and Docker on PATH. Do not run it against an existing cluster of the same name without checking it first. Tear down with `kind delete cluster --name pulsestream`; application data in that cluster is deleted. To remove only the application while preserving dependency PVCs: `helm uninstall pulse -n pulsestream`.

The checked-in `deployments/kubernetes/pulsestream.yaml` is generated by `helm template pulse`. Regenerate when changing chart values/templates. Helm lint and strict kubeconform validation were executed; the final check covered 50 resources including an optional Ingress/PDB rendering. A real single-node Kind deployment also passed public API count/revenue/failure checks, consumer membership, alert lifecycle and browser WebSocket verification. See [deployment evidence](evidence/kind.json). The temporary validation cluster was removed afterward. KEDA requires its operator/CRDs to be installed. Enable `keda.enabled` only with a working installation, valid Kafka connection/security configuration and suitable broker reachability. No KEDA CRD is installed by default. The scaler caps replicas at the configured partition count; extra replicas otherwise cannot add useful per-partition parallelism. No custom utilization-based scaling or certified production autoscaling policy is claimed.

Default NetworkPolicy admits namespace-local callers and dependency ports. Cross-namespace ingress controllers, telemetry or external databases require explicit policy edits. For a development port-forward this is sufficient; a production ingress must configure TLS and authentication boundaries. The optional Ingress uses `pulse.local` for dashboard/analytics and `ingest.pulse.local` for ingestion to avoid HTTP method routing conflicts. Set PULSE_ORIGIN to the deployed dashboard origin.

The init Job retries up to six times; Helm has no dependency chart for external databases. Application migrations are also serialized through a PostgreSQL advisory lock during startup. Topic creation uses replication factor one and is suitable only for the supplied dev topology; production topics must be explicitly provisioned with the desired replication before app deployment. The init role checks partition counts and existing schema.
